## Decisions and defaults taken (all revisable)

1. `MIN_PAYOUT_IDR` 100 000 (placeholder, D-22 item 3); hold 72 h (D-19); claim lease 30 min; seller step-up window 300 s (same as T-60). All in `ledger/settings.ts`.
2. OPEN-F3: a COD booking reserves its `shipping_debit` as `pending` when available cannot cover it. OPEN-F6: the carried debit of a parcel that earned no sale is netted by `ledger.release` against `available`, never below zero; the remainder waits for a four-eyes `adjustment`.
3. The seller has no `complete` action; `claimDelivery` only records a claim. `completed`/`returned` come from `applyProviderTransition` (courier DELIVERED/RTS or the four-eyes `cod.manual_complete`). The database mirrors the legal-move table (`order_status_guard`).
4. `payout` is class `tenant` (not `restricted`) until T-59b, like the T-60 tables; bank values are read by operators only through `withPersonalDataAccess`, lists carry the last four digits.
5. Seller step-up proof: new table `store_step_up_proof` plus definer `issue_store_step_up` (re-derives session, owner membership and the session's own MFA record).
6. Fake COD courier: the migration seeds SPX only (UNVERIFIED, OPEN-F7); the local seeds, the test database and the scratch contract database register the fake courier JNE (`ledger/fixtures.ts`).
7. New `ledger_entry.release_basis` values `netting` and `direct` (entries born available: payout debit/reversal, adjustment, an `available` shipping debit) beyond `delivery`/`reconciliation`; the invariant "released entry carries `released_at` and `release_basis`" holds for all.
