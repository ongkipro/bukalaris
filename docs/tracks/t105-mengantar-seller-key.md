## Scope and invariants

ADR-0013 sections 4, 5, 7 and 9 (decisions 9, 10, 15 to 17, 28 to 34), C-P1, C-P2, C-P4, C-P6, C-P7, C-P10, D-27, D-31 to D-33. Each invariant has a named test in `packages/db/test/t105-mengantar-seller-key.test.ts` (16 tests):

1. **One client, key stripped from every error.** Quotes, area search, pickup registration, booking and tracking of a `seller_owned` store go through `SellerMengantar` (`shipping/seller.ts`). Every method re-throws through `scrubKey`, which rebuilds the error with the raw, URL-encoded and JSON-escaped key removed from message, body and provider code; the key travels URL-encoded in the path only. The T-48 Partner-Secret entry gate does not apply to a seller's own key (ADR-0013 section 8); it still guards every platform-credential call.
2. **One eligibility function.** `sellerMethods` (pure) produces the buyer's method list through `sellerShippingOptions` → `shippingOptions`, and `placeOrder` re-runs that list and checks the choice with `chosenShippingFee`. A courier without a rule row is closed; cargo services, zero/missing prices and unsupported routes are dropped; COD needs the store switch, the courier's COD switch, the route, the platform ceiling (C-P2: a disabled or COD-refusing `courier_service_policy` row lowers it, no row does not, `return_free` is dropped) and a resolved, unblocked province. An area whose province was never answered by a provider area search is unresolved and refuses COD.
3. **Prices.** The buyer pays the provider's public rate (`price`; without it the undiscounted estimate minus any COD fee), margin 0, no platform discount. The estimate never carries `COD_AMOUNT`. The form sends back the fees it showed (`shippingQuote`), required for a store on its own account; submit refuses a missing list, a changed price or a courier the buyer was not shown (`quote_changed`) and creates nothing. Buyer-driven provider calls on a seller's key are limited before the call: per client IP first (area search 60, quotes 120 per 10 minutes) and a per-store cost ceiling sized far above normal traffic (3000 and 6000), because a full store bucket blocks every buyer of that store; the seller's own pickup-area search has its own bucket (120 per 10 minutes) and never shares the buyer one (doc 16 RL-SELLER-AREA / -QUOTE / -PICKUP, proposed starting values, with the lockout trade-off).
4. **Booking.** A seller action with a pickup type (scheduled pickup or drop-off) on the store's own key; one provider write at a time per store (dispatch lease `seller:<account>`); one shipment per order. On the store's own account, timeouts, dropped connections, provider 5xx, an unreadable success and a lost worker make the shipment `unknown`: no seller rebooking and no job re-run until the seller, who can inspect that account, releases it (reason, audited) or links the order the provider accepted (its order id only, audited). A link first reads that id on the store's own key: an id the provider does not know is refused and the shipment stays `unknown`; a known id is stored, and only the resi a tracking read returns ships the order. An uncertain pay-unpaid of an unpaid order stays `awaiting_balance` with its own message (retrying it cannot create a second order). One provider order belongs to one shipment of the store (`shipment_provider_order_uq`). An order on a platform account keeps the T-39 rule (uncertain → `failed`, the seller asks Bukalaris before retrying) and can be neither released nor linked by a seller (review M1). Each attempt sends its own `idempotencyKey` header (`bk-<store>-<order>-<attempt>`). The Q-17 COD gate, the free-return COD list and the platform shipping-cost reservation do not apply to a store on its own account.
5. **COD refusal.** A provider 403 refusing COD for the seller (documented body status `new_seller` / `insufficient` / `blocked`) switches that courier's COD off for the store (`cod_refused_at` set), mails every owner and shows the refusal on the courier; only a courier form that showed the refusal turns it back on (a stale form keeps it off).
6. **Production switch (ADR-0013 decision 34, C-P4).** `provider_live_setting` (row `mengantar`): off by default; switching it ON needs a recorded sandbox pass (service and database check) and four-eyes with the action shared with T-106 (`providers.production_on`, capability `providers.manage`, target id = the provider: the requester files it, a second operator approves it in SA-28, the requester consumes it once). The approval payload (`provider`, `enabled`, `sandboxPassAt`, `revision`, the T-106 shape) binds it to the recorded pass and revision, so a new sandbox pass voids it; switching OFF is immediate; every change is an audited Owner-console mutation with a reason. While it is off, no call is made on a seller's production key (quotes, registration, booking, tracking, the live connection check).
7. **Readiness columns (T-104 known gap), narrowed, not closed.** `provider_account_guard` bounds the application role: a check time and a pickup registration carry the statement's own time, a passed check carries its check time, a registration needs a connected key whose last check passed and a provider pickup id (`shipping_account_pickup_chk`), and a key or environment change clears the registration for every role. Code running as `bukalaris_app` can still record `last_result = 'ready'` with `now()` for its own store without a provider call: the writes stay app-side as a deliberate ceiling (`docs/DECISIONS.md` D-34, with the upgrade path to worker jobs).
9. **Onboarding order (review M2).** A new seller connects the key first: without a pickup area the live connection check reads the account's keyed pickup-address list (`GET /address`); with one it is the decision-8 rate estimate. The pickup area is then searched on the store's own key, and the province cache is kept per environment (sandbox never overwrites production).
8. **Test-order marker (C-P10, decision 11).** `order.test_order` is set at submit when the order's account is a sandbox account and never changes afterwards (`order_test_marker_guard`, any role).

- Webhooks, the full status set and the dedicated-account check are T-115.
- The order page does not show the test-order marker yet (the order view is `seller/commerce/orders.ts`, outside the Allowed Paths); T-107 consumes it for sales figures.
- Platform-account bookings keep the T-39 uncertain-outcome rule (failed, the seller asks Bukalaris); an operator-side recovery tool for them is not built here (out of scope).
- Province resolution reads the province of an area from the store's own provider search; a destination never searched through the store (for example an order created by API without a search) refuses COD.
- Seller Admin copy for an own account avoids the brand name outside `/seller/payments` (the T-48 copy guard); the shared shipment timeline still says "Resi terbit dari Bukalaris Kirim" and `whiteLabel` still rewrites provider text for these stores. T-107 moves that copy boundary.
