## Scope and invariants

ADR-0013 section 11 (decisions 40 to 45), decisions 30 and 31, C-P1, C-P3, D-32 item 7, D-33, doc 16 RL-MENGANTAR-WH and RL-TRACK-REFRESH. Each invariant has a named test in `packages/db/test/t115-mengantar-lock.test.ts` (21 tests):

1. **Mengantar is the only shipping aggregator (decision 40).** Every `store_shipping_account` kind is a Mengantar account (`SHIPPING_PROVIDER = "mengantar"`), the database check refuses any other kind, the AutoLaris key writes only the payment account, and no seller or Owner-console shipping screen or shipping module names another aggregator or offers a provider choice. Test: "no provider other than Mengantar can be connected for shipping …".
2. **A new, dedicated account (decision 41).** Connecting a key to a new account (a new key or another environment) reads one page of the account's order list on that key (newest 100, archive included through a date range back to 2015): any order Bukalaris did not create for this store refuses the account and nothing is stored (`account_not_empty`); an unreadable list refuses too (`account_check_failed`). The seller's confirmation (`confirmDedicatedAccount`, owner) re-runs the same check, is recorded for that key fingerprint and environment only (`store_shipping_sync.dedicated_*`) and is a readiness gap (`dedicated`) until given; another key needs it again. Tests: "the connection check refuses an account that already holds orders; nothing is stored"; "the seller's dedicated-account confirmation is recorded for the connected key and environment only …".
3. **Foreign parcels (decision 41).** The account scan (worker, store's key) compares the newest orders with every provider order Bukalaris created for the store (`shipment.provider_order_id` and the status history, so a released and rebooked parcel is never foreign); an unknown one becomes a `shipping_foreign_parcel` row, never an order or a shipment, and the store's sync is "not exact" until the seller resolves it with a note (audited). Test: "a parcel in the account that Bukalaris did not create is listed as foreign, not imported …".
4. **Two paths, one writer (decision 43).** The webhook route resolves the store from the opaque id of its address (`resolve_mengantar_webhook_store`, definer, app pool), opens the store's sealed Webhook Secret (`provider_key_envelope(store, 'mengantar_webhook')`, bound to the connected key and environment), verifies `x-signature` (HMAC-SHA256 hex of `{x-timestamp}.{raw body}`, constant time; the documented test vector passes), refuses a timestamp more than 5 minutes off and `x-environment: sandbox` for a production account, limits per store after the signature (RL-MENGANTAR-WH), stores the event once (signature unique per store) and only enqueues `shipment.track` for that store's parcel (one per parcel and minute). The tracking read is the single writer: it re-reads the shipment under lock, never moves a final parcel, ignores a parcel booked again meanwhile and an answer whose `lastStatusChange` is older than the applied one. Tests: "a verified webhook … is stored and only enqueues a tracking read on the store's key; the read is the single writer"; "forged, unsigned, stale, replayed, out-of-order and sandbox-marked webhooks change nothing by themselves"; "racing reads cannot move a parcel back …"; "a webhook for store A cannot move store B's parcel".
5. **The scheduled read (decision 43).** Each minute `shipping.parcel_sweep` enqueues a read for every non-final parcel on a store's own account not read for 30 minutes, the stalest parcel of each store first (fair across stores), at most 100 per run, idempotent per staleness window; a paused webhook only slows the state down. Test: "missed webhooks are repaired by the scheduled read: every non-final parcel is read, the stalest of each store first".
6. **The whole parcel life through one table (decision 42).** `shipping/parcel-state.ts` `PARCEL_STATE_MAP` maps each documented `status_category` to one of the eleven states of decision 42; the default branch maps nothing, so an unknown category keeps the shipment's state, is stored raw (`shipment.provider_status`, `shipment_status_event.category` with `parcel_state` null) and is shown as received to the seller (`displayableCategory`, status codes only). Every observed category is appended to `shipment_status_event` with its source and the provider's change time; Mengantar's own `history[]` stays on the shipment. Tests: "each state of decision 42 … comes from the one table"; "each state through the single writer on the store's own account …"; "an unknown status category stays raw …".
7. **State effects (decision 44).** Delivered completes the order (prepaid or COD; a COD order gets `paid_at`, C-P1); RTS returns the order (stock back as built in T-39); pickup failed and error mark the parcel `problem` and leave the order; a courier cancellation on the store's own account **releases the booking**: the shipment is `cancelled`, the order goes back from `shipped` to `processing` with the resi cleared (a new legal move in `order_status_guard`, only for `seller_owned` orders and only for the courier writer), and the seller may book again (a new provider order; the cancelled one stays in the status history). A platform-account order keeps the T-39 rule (cancelled). Test: "each state through the single writer …".
8. **The Webhook Secret is sealed like the API key (section 2).** Owner (`integrations.manage`) with a fresh step-up (subject `mengantar_webhook`) consumed in the writing transaction; the database guard `store_shipping_sync_guard` refuses a secret change by the application role without that proof; the application role has no SELECT on the sealed secret, its key id or the step-up reference; audit rows carry an HMAC fingerprint only; every owner is told. Test: "the Webhook Secret … never appears in an error, a log, an audit row, a job, a mail, an event or a view" (canary secret, literal scan over every table, the console and every captured error).
9. **Mengantar's money figures (decision 45).** The account scan mirrors the balance and the 20 newest invoices (documented fields only, the `user` block dropped) with the read time into `store_shipping_sync`; the application role reads but cannot write the mirror. Per-parcel figures: only the fields the documentation shows (`PROVIDER_FIGURE_FIELDS`: `estimatedPrice`, `estimatedSpecialPrice`, `discount`, `COD_FEE` from the create-order answer; `COD_AMOUNT`, `GOODS_AMOUNT` from the order read), stored with their read time for a store's own account; anything else is dropped. Test: "Mengantar's balance and invoices are mirrored read-only with the read time; per-parcel figures only for the documented fields".
10. **RL-TRACK-REFRESH** for a parcel on the store's own account: 1 per 5 minutes per parcel, 60 per 10 minutes per store. Test: "a seller's read-now is limited per parcel and per store (RL-TRACK-REFRESH) …".
11. **Status codes only (review major 2, T-47).** A provider status can be free text naming the receiver. `shipment_status_event.category`, `shipping_webhook_event.status_category` and `shipping_foreign_parcel.provider_status` store a status code (a category of the one table, or an upper-case code by the redaction rule `PROVIDER_CODE_RE_SOURCE`, at most 40 characters) or the redaction marker, never the text; the seller screens show codes only (`storableCategory`, `displayableCategory`). The T-47 free-text guard now covers every T-115 shipping table. Test: "a provider status that is not a status code (it may name the receiver) is never stored or shown as received …".
12. **An unpaid booking cancelled in the seller's account is released (review major 3).** On a store's own account a CANCELED/CANCELLED read without a resi makes the shipment `cancelled` (the order keeps its status), the sweep stops reading it, and a new booking creates a new provider order instead of paying a deleted one. Test: "an unpaid booking cancelled in the store's own account is released without a resi …".
13. **Seller-held money is not platform money (review major 4, ADR-0013 section 8, C-P1).** In the single order writer, a COD order on a store's own courier account books no platform COD sale when delivered, and a returned or courier-cancelled order whose COD cash or prepaid payment (T-106 attempt with `payment_account_id`) reached the seller's own account opens no platform refund and reverses nothing (`sellerHeldMoney` in `seller/commerce/orders.ts`, minimal and named; T-107 builds the full boundary). Test: "money that reached the seller's own accounts is never booked or refunded by the platform …".
14. **Forward order without a change time (review minor 5).** When either answer lacks `lastStatusChange` (UNVERIFIED on a single read), a read never moves a parcel to a lower rank among the non-final states (created < waiting for pickup = pickup failed < picked up < in transit < out for delivery = UNDELIVERED < returning). Test: "without the provider's change time, a read never moves a parcel back …".
15. **An unknown booking and a foreign parcel (review minor 6).** While a booking's outcome is unknown, a foreign parcel that appeared after that booking started (or of unknown age) cannot be marked handled, and the unknown booking cannot be released while such a parcel is open: the seller links it. Older foreign parcels stay resolvable. Test: "while a booking's outcome is unknown, a parcel that appeared after it started can be neither marked handled nor used to release the booking …".
16. **Unreadable order ids (review minor 7).** An order whose id cannot be read refuses the account at connection and is listed by the scan as one foreign marker (`TIDAK-TERBACA`). Test: "an order in the account whose id cannot be read refuses the account at connection and is listed as foreign by the scan".

## Open points

- **Categories for "in transit" and "returning to sender" are not mapped** (Order Status Reference Sheet not read): those parcels show the raw category until a row is added to `PARCEL_STATE_MAP`; the effect of `returning` (no order move until RTS) is in place.
- `lastStatusChange` and `statusCategory` on the single-order read are UNVERIFIED; without `lastStatusChange` the stale-read guard falls back to "a final parcel never moves" and the forward rank of the non-final states (review minor 5).
- Retention classes are named, not built: `shipping_webhook_event` (webhook evidence) and `shipment_status_event` (status history). Their purge functions and periods join the T-74 framework with the privacy owner (docs/13 not in the Allowed Paths).
- **Rotation hazard (review minor 9, kept open):** the shipping-ring re-seal job (`resealShippingCredentials`) re-seals API keys, not Webhook Secrets. If the old ring key is dropped while a store's secret is still sealed under it, the envelope no longer opens, every delivery is answered 401, and Mengantar pauses that store's webhook after 20 failed deliveries within 24 hours (missed updates are not resent; the scheduled read keeps the parcels correct, only slower; the seller reactivates in Mengantar after re-entering the secret). Before dropping a ring key: re-seal or re-enter every Webhook Secret, or add them to the re-seal job. (`docs/RUNBOOK.md` is outside the Allowed Paths, so the note lives here.)
- The seller-held money guard covers the courier writer only (review major 4). A seller's own cancel through `applyTransition` (`orders.ts` `cancel`) still calls `settleTerminalOrder`; the full money boundary for `seller_owned` stores (no ledger, no platform refund anywhere) is T-107.
- Minor 6 edge: if an unrelated parcel appears in the dedicated account after a booking whose outcome is unknown, the seller can neither resolve it nor release the booking; linking is the only path. This only happens when the account is used outside Bukalaris, which decision 41 forbids; support resolves it.
- The unreadable-id marker (`TIDAK-TERBACA`) is one row per store: once resolved, a later unreadable order does not reopen it.
- Cancelling an order in Bukalaris does not delete the Mengantar order (no `DELETE /order` call); the seller cancels in Mengantar and the read releases the booking.
