## Decisions taken (defaults, revisable; none is an owner decision)

1. **Case numbers** are `C-000123` (generated column), cited by id or number. An action cites an OPEN case that names the target (or, for a store case, a member of that store). A store lifecycle change takes a case only optionally (the verification record and risk queue are informational); every identity action and every reveal requires one.
2. **Suspension** of an identity is a new column `user.suspended_at`, written only by the owner-side function. It ends every session in the same transaction, `sellerContext` refuses it, and the Better Auth `session.create.before` hook refuses new sessions on every surface. The DATA-14 text allowed this column "only if the auth schema has none"; the auth schema had none.
3. **Recovery link** lifetime one hour (`SUPPORT_RECOVERY_TTL_SECONDS`, same as the reset token). The token exists as SHA-256 only, in `support_recovery_link`, readable by nobody but through `support_recovery_redeem()`. The redeem page is a button (a mail scanner that prefetches the link cannot burn it); a redeemed link becomes a Better Auth reset token valid for 15 minutes, so the password is only ever typed by its owner. A suspended identity, a staff identity and an unverified contact never get a link.
4. **Reveal window** 300 s (`REVEAL_WINDOW_SECONDS`); search limit 30 per 10 minutes per staff (`ACCOUNT_SEARCH_LIMIT`, `ACCOUNT_SEARCH_WINDOW_SECONDS`, RL-ACCT-SEARCH). Named conservative defaults (D-22 item 3). The in-window re-read is itself a `full` access event bound to the original case and purpose.
5. **MFA reset**: a store-owner account needs four-eyes (`mfa.reset`): the request is recorded ("menunggu penyetuju kedua"), a different `accounts.support` holder approves the exact payload, only the requester executes, once, and the `support_action` row can become `executed` only because the trigger sees that executed approval. A team member who owns no store is a single-approver action with case, reason and a notice to the contact (IAM-15). Staff are reset only through `staff.manage` with four-eyes `staff.mfa_reset`, never through `accounts.*`; the owner-side function enforces the target class. A rejected or expired approval cancels the action as a written outcome (`mfa_reset_cancelled`), not an error.
6. **Break-glass**: requested and executed by the requester (`break_glass.approve` holder), approved by a different holder (`breakglass.approve` four-eyes); the grant binds one target and one case; allowlist and two-people checks are the existing CHECKs; every use is an access event naming the grant; all `audit.read` holders get a mail at grant time (ids and times only); a review record after the end by someone else, once. **No duration maximum is invented** (PRIV-9 leaves it OPEN): the requester chooses the length, the approver sees it in the payload.
7. **Staff deactivation** is `platform_operator.deactivated_at`: one transaction revokes every grant (with events), cancels the open requests, deletes sessions and sets the flag; `operatorScope` returns null from then on. The row stays, so the identity is still staff and never an `accounts.*` target. Reactivation restores the scope, not the grants.
8. **Access-review last use** is a stamp written when a console operation passes the capability check, at most once per 300 s per grant. "Never used" is shown as such (NULL), including for grants older than this feature.
9. **Search is a POST**, not a GET (contact text in URLs ends up in history, referrers and proxy logs). Phone queries are canonicalized (`08…`, `62…`, `+62…`) but seller team accounts carry no phone, so they match nothing until a verified phone exists.
10. **Masked store team** in `getStoreDetail` is a behaviour change for SA-03 (emails were shown in clear before). The audit reason of store creation no longer carries the owner's e-mail.

## DEFERRED (with the exact missing decision or fact)

- **Staff invitation by e-mail and staff account creation** (SA-38): needs the operator identity tables and their own Better Auth instance (T-59b, D-20 item 6). Deactivation, grants, MFA reset and reviews are built on the current `platform_operator` row.
- **Default grant of `ops.issues.report` to every active staff member** (carried over from T-62): belongs to the staff creation path above.
- **SA-17 store ledger statement**: needs the ledger (T-37); the store detail states "belum tersedia", the capability gating (`finance.read`) is not wired.
- **"Resend verification"** (SA-24): the platform has no e-mail verification flow to resend into (Better Auth's `emailVerification` is not configured and sign-up is disabled); building a link here would mint a credential-bearing mail with no consumer. Needs the decision to enable Better Auth e-mail verification.
- **Break-glass duration maximum and review deadline**: PRIV-9 leaves both OPEN; none is invented (the duration CHECK stays absent, the review queue has no overdue marker).
- **Risk rules over sources that do not exist yet** (subscription state T-50, shipping account T-48, payout age T-37, affiliate counters T-52): listed as unavailable on SA-18, never counted as zero. No age or ratio threshold is invented.
- **SA-53 COD reconciliation queue** (the Added assertions of the TASKS item name it): its data (delivered COD orders, carrier invoice lines, `cod.reconcile_release`) is T-37's; not built here.
- **Seller-facing consented support grant** and **affiliate and buyer kinds**: T-72 / OPEN in ADR-0011.
- **Operator step-up proof for these actions**: the T-62 approvals inbox consumes a proof for approval decisions; the account actions here rely on the MFA-bound session (`operator()` requires `session_mfa`). A per-action fresh-code requirement needs the audited fresh-authentication window setting of SA-34 (T-62 DEFERRED).
- **Contract step** (`t59-contract.sql`): the new platform grants are in the file and proven on the scratch schema; applying it still waits for the owner (D-22 item 4).
