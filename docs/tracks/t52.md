## How it works

- **Resolver (one, in the database).** `affiliate_resolve_core` is the only place that decides: valid typed code wins; else the latest eligible click among the ≤ 5 ids of the cookie (capture time, then larger id) of THIS store inside its own frozen window (end exclusive); eligible = account active, store has not blocked it, selector active. A chosen affiliate whose canonical phone (T-57 SQL port `buyer_canonical_phone`, read from the order row, never passed in) equals the buyer's earns nothing and nothing else is tried. Parity with `samePhoneIdentity` is tested.
- **Order transaction.** After order, lines and stock: resolve (share-locks the affiliate) → per-product live rate via `affiliate_line_rate` (same function the guard re-checks; 0 unless store policy open, offer active, product published, store active, rate inside programme bounds) → `calculateAffiliateCommission` from the frozen `order_line_financials.commission_base_idr` (the BILL-4 allocation, not re-allocated) → `withAffiliateCommission` → `writeOrderFinancials` with `affiliate_id` and per-line `commission_rate_bps` → `affiliate_record_attribution`, which re-runs the selection and re-derives every rate itself; the attribution guard re-proves the single floor from the snapshot; a deferred constraint at COMMIT makes "deducts a commission" and "has an attribution" inseparable. Buyer `payable` never moves; `sale_amount_idr` falls by the commission.
- **Never fails an order for a selector.** Unknown, malformed, expired, revoked, blocked, forged, self-referral: order placed, no attribution.
- **Click entry `GET /r/[token]`.** Destination from the link record only; capture only for GET + `Sec-Fetch-Mode: navigate` + `Sec-Fetch-Dest: document`, no prefetch; RL-CLICK 120/10 min per IP, 600/10 min per link (over the limit: redirect, no click, counted once per window); unknown/revoked/expired/blocked/suspended → one identical not-found; cookie `__Host-bl_click` (`bl_click` outside production), HttpOnly, SameSite=Lax, host-only, lifetime = the click's own window; ids opaque (`c` + 128 random bits from the database), server-timestamped, bound to link's affiliate AND store by composite FKs; no IP/UA/referrer/URL stored on the click.
- **Isolation.** The app role has no INSERT on click/attribution/catalog/counter/policy; it cannot read the raw click log at all, and reads attribution only through a column grant that omits `order_id`, `click_id`, `code_id`. All writes are definer functions that derive ids from the database and re-check `app_store_id()`; `affiliate_capture_click` takes only the public token.
- **Projection (JOB-20).** Triggers bump the offer revision on every offer write and on product title/slug/status, variant price or sold-out crossing, and image changes, leaving one ID-only job per revision; a seller-policy change leaves ONE store-wide job and touches no offer row (deliberate: updating offers from the policy trigger created a lock cycle with a concurrent checkout; the ordering test `seller edits and orders never deadlock` guards it). The handler reads the live rows on the platform pool with an explicit store; the catalog write is refused unless `(offer revision, store policy revision)` grows (trigger + `ON CONFLICT … WHERE`).
- **JOB-27.** `retention.affiliate_click` is registered (class, sweep, daily schedule, kind) with NO period row: it deletes nothing until the privacy owner records one through `retention_set_period`. With a period it detaches the attribution's click reference, then deletes the click; financial evidence, ledger and aggregate counters are unchanged (tested).

## Defaults taken (NAMED settings, none is an owner decision except where marked)

| Setting | Value | Status |
|---|---|---|
| `AFFILIATE_ATTRIBUTION_WINDOW_DAYS_DEFAULT` | 7 | PLACEHOLDER (ADR-0009 OPEN; "30 days is not an accepted default"); snapshotted on click and attribution |
| `AFFILIATE_HOLD_DAYS_DEFAULT` | 3 | DECIDED (D-14/ADR-0009); snapshotted on the attribution, consumed by T-53 |
| `AFFILIATE_MIN/MAX_RATE_BPS_DEFAULT` | 100 / 2000 | PLACEHOLDERS (no invented initial rate: a seller's default rate is NULL until chosen) |
| `RL_CLICK`, `RL_CODE` | 120/600 per 10 min; 10 invalid/10 min/cart | from 16-OBSERVABILITY |
| `CLICK_COOKIE_MAX_IDS` | 5 | named |
| `AFFILIATE_RISK_THRESHOLDS` | 3 / 20 / 200 / 0.5 / 5 | PLACEHOLDERS (SEC-20: thresholds OPEN) |

Seeded into `affiliate_policy` by the migration; `t52-schema` pins the row to the constants; `t52-literal-scan` fails on any other window/hold/rate/fee literal in `src/affiliate`. Other decisions: an attribution exists only when the commission is > 0 (a zero base or no opted-in line creates none); a commission that would leave the seller less than the shipping discount they fund is not earned (the order still places); `commission_base_idr` is the sum of the bases of the lines that earn; a click whose link is later revoked stops counting, a link's own expiry only governs capture; suspension is derived from the account row (reactivation restores links); the platform fee on commission is NOT applied (the snapshot is the gross commission).

## DEFERRED (exact missing decision)

1. **Cross-origin click continuity** (storefront or checkout origin ≠ apex, e.g. host mode): the cookie is host-only on the apex, so link attribution works only where the checkout shares the origin (path mode, e2e); a typed code works everywhere. Needs the security/privacy owners' decision on first-party storage and the validated referral handoff (ADR-0009 open row).
2. **Window length, rate bounds, risk thresholds, platform fee on commission, click retention period, notice text** (PRIV-5/PRIV-7): product/finance/privacy owners. Defaults above; fee not applied; JOB-27 OFF.
3. **Programme-limit writer** (`affiliate_policy` four-eyes `affiliate.rate_bounds`) and all screens (affiliate portal, seller opt-in UI, Owner review): T-54.
4. **Commission state effects** (void on cancel/return before delivery, `eligible_at`, credit, wallet, payout, platform fee): T-53. The attribution columns and guard exist; no writer.
5. **SA-18 wiring**: counters and `affiliateFraudFlags` exist, but the queue is per store and the flag is per affiliate; the console must decide the shape and thresholds. `affiliate_fraud` stays `available: false` (t63 test unchanged).
6. Affiliate storefront tables and link targets of an affiliate storefront: T-54.

## Known ceilings

A compromised app-role session could call the three checkout definer functions with any code/order of its own store (equality oracle on affiliate phone; counter inflation); amounts and affiliate cannot be chosen. `rate_limit` keys hold client IPs as the other limiters do. The catalog rebuild requires `ops.jobs.manage` and does delete-and-reinsert (platform holds DELETE on that one table only).
