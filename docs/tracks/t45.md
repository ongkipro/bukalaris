## What changed

### T-47 (PR-4, SEC-19, PRIV-1, PRIV-4, TEN-1, TEN-3)
- `BUYER_DATA_INVENTORY` has `shipment.tracking_history` (strip), `shipment.provider_status` (strip), `shipment.last_error` (redact). The privacy doc table (`docs/13-COMPLIANCE-PRIVACY.md`) has the matching rows; the existing inventory test already fails for an undocumented entry, and the new test fails for a free-text `shipment` column that is not in the inventory.
- Buyer export (`exportBuyerData`): each order has `shipment` (status, courier code, resi, COD amount, weight, provider status, tracking history, last error, paid, booked/delivered/last-tracked timestamps; provider order/batch ids and the requester are left out) or `null`.
- `redactOrders` / retention (`redactRows`): every tracking line keeps `at` and any key other than `desc`, `desc` becomes `[dihapus]`; `last_error` becomes `[dihapus]` when present; `provider_status` stays while it is an upper-case status code (`^[A-Z]+([ /_-][A-Z]+)*$`, at most 40 characters) and is replaced otherwise. Status, resi, courier, amounts and every timestamp are untouched; an already stripped row is not selected, so a second run changes nothing. The audit row `privacy.redact` carries `shipments` and `checkoutSessions` counts.
- `shipping/fulfillment.ts` `applyTracking`: a poll of an order that already has an `order_redaction` row (override on an open order) stores its new lines already stripped (otherwise the next poll would refill provider text).
- `storefront/signals.ts` `purchasePayload`: a `[dihapus]` name or phone is never hashed (before: `sha256("dihapus")` was sent as `fn`, the same value for every redacted order).
- `.env.example` documents `MENGANTAR_PICKUP_ADDRESS_ID`, `MENGANTAR_PICKUP_TIME_ID`, `ALLOW_COD_BOOKING`, `BUYER_DATA_RETENTION_DAYS` (commented placeholders) and the new `KEYRING_CHECKOUT_RESUME` (dev placeholder).
- `pnpm db:seed:demo`: per demo store a published landing page (hero, benefits, order block on the first active product), one active feed token and one booked fake shipment with tracking (the plan's paid `placed` transfer order goes through the real `bookShipment` path with the in-process fake courier, which `seedDemo` forces with `setBookingAdapter`, then one `refreshTracking`). No login role got any new DELETE: the reset still removes shipments through the generic loop and the ledger/payment/shipping evidence through the existing owner-only `reset_demo_*` functions.

### T-45 (PR-25, DATA-8, PRIV-1, PRIV-4, TEN-1, TEN-3, SEC-16, UX-15)
- Table `checkout_session` (`seller/commerce/schema-abandoned.ts`), FORCE RLS `tenant_isolation`, one row per cart, `public_id` random handle for the link (never the primary key), `status` `active|abandoned|recovered`, contact columns, server-computed `subtotal_idr`, `abandoned_at`, `recovered_at`, `wa_opened_at`, `created_at`, `updated_at` (= last buyer activity).
- Grants: app SELECT, INSERT, UPDATE (capture, recovery, the WA stamp, redaction; no DELETE); platform SELECT, UPDATE, DELETE (cleanup sweep and purge; also in `drizzle-pending/t59-contract.sql`). No definer function is callable by a login role; the one new definer function is the trigger guard `checkout_session_guard()` (owner, pinned `search_path = pg_catalog, pg_temp`, qualified names, `execute: []`, registered in `DEFINER_FUNCTIONS`).
- `checkout_session_guard`: a new row starts active and unstamped; identity (`id`, store, cart, `public_id`, `created_at`) is immutable; `recovered` is final; both stamps are written by the database clock, are monotonic and cannot be set by a caller; `active -> abandoned` only after 60 idle minutes and without moving `updated_at` (so no caller can inflate the Abandon Rate); `abandoned -> active` only with new buyer activity (`updated_at` moves) and keeps `abandoned_at`; "WA dibuka" only on an abandoned row.
- Capture (`captureCheckoutSession`, server action `captureProgress` in `(checkout)/checkout/actions.ts`, client `capture-progress.tsx`): the client listens only to `input` events of the four contact fields and reports after 1.5 s of quiet; nothing is sent on page load or for an untouched form, and the server stores nothing for an entirely empty form either. Cart from the HttpOnly cookie, store resolved from the cart, subtotal recomputed from the cart rows. A phone that is not yet a valid number (T-57 `phoneLookupKey`) or an invalid e-mail (`normalizeEmail`) is stored as NULL while the buyer types. Limits: 60 per cart and 300 per IP per 10 minutes, dropped silently. A visible notice on the checkout form (Indonesian) says what is kept, for at most 30 days, for the store, and not shared with ad platforms. Nothing is ever sent as an ad event.
- Sweep and purge (`sweepCheckoutSessions`, run first in `cleanup.ts`): `active` idle >= 60 minutes to `abandoned`; rows with `created_at` older than 30 days deleted (task text; constants `CHECKOUT_SESSION_IDLE_MINUTES`, `CHECKOUT_SESSION_PURGE_DAYS`). `cleanupIdleCarts` keeps a cart a session still references, so the resume link and the counts survive the 7-day cart sweep. Schedule `cleanup.ts` at least every 15 minutes (an ops decision, below).
- Recovery: inside the order transaction of `placeOrder`, the session of that cart becomes `recovered` (`recovered_at` stamped by the guard, `abandoned_at` untouched) and drops its typed contact (it now lives on the order). A straight-through checkout is `recovered` with `abandoned_at NULL`, so it is never a rescue.
- Rates (`abandonRates`, pure, table-driven): Abandon Rate = abandoned / (abandoned + orders), Recovery Rate = rescued / (rescued + abandoned), where `abandoned` = sessions with status `abandoned` right now, `rescued` = `abandoned_at IS NOT NULL AND recovered_at IS NOT NULL`, `orders` = every order of the store in the window; integer basis points, `null` (shown as "—") for a zero denominator. Window: sessions created and orders placed in the last 30 days (the purge age, so no counted row is purged early). Active sessions are in neither count.
- Ranking (`rankAbandoned`): usable phone first (T-57 key), then `subtotal / (1 + minutes_ago / 1440)` since the last activity, then newest id. Queue: the best 100 abandoned sessions.
- `/seller/customers/carts` (SC-26): two rate cards, the ranked queue (name, phone, value, last activity, products, "WA dibuka" badge) and a per-row "Hubungi lewat WhatsApp" server action (`openWhatsApp`). Capabilities `carts.read` and `carts.recover`, both owner and staff (they already read buyer phones on the orders they fulfil). `carts.read` is in `BILLING_READ_ONLY_ALLOWED`; `carts.recover` is not (the stamp is a write: the button is disabled and the service refuses with `billing_read_only`). Nav entry "Keranjang tertinggal".
- WhatsApp (`openWhatsAppRecovery`): only an abandoned session of this store (RLS) with a usable phone; stamps `wa_opened_at`; returns `https://wa.me/<62… key>?text=<Indonesian message>`; the message names the store and says the cart is still saved and the link lasts 7 days; no promise of delivery, stock or price.
- Resume link (`signResumeToken`/`verifyResumeToken`/`resumeCheckout`, route `GET /checkout/r/[token]`, HTTP-32): `v1.<key_id>.<store_id>.<public_id>.<expiry>.<HMAC-SHA256 base64url>` under the new key ring `KEYRING_CHECKOUT_RESUME` (first key signs, all verify; missing/malformed/duplicate id or a key shared with the buyer-fingerprint, integration or shipping ring fails closed). The MAC covers purpose, key id, store, handle and expiry. Redemption verifies without a database, then looks the handle up inside THAT store's RLS context, so a validly signed pair that names another store's session finds nothing. A valid link only binds the saved cart to the buyer's per-store cart cookie and lands on `/checkout?store=<slug>`; nothing of the buyer is shown or prefilled. Every failure (malformed, unknown key, signature, expired, unknown session, recovered, cart gone, store unavailable, rate limited at 60 per IP per 10 minutes) is the same safe page (SF-10) and sets no cookie.
- `checkout_session` is in `BUYER_DATA_INVENTORY` (name, phone, e-mail, address; handling redact), exported by phone or e-mail match (`checkoutSessions`, without the handle, cart or ids), overwritten by `redactOrders` for the order's own cart and for the same buyer's other sessions (name, phone, address `[dihapus]`, e-mail NULL, matched through the T-57 SQL key `buyer_phone_key` / lower-cased e-mail BEFORE the order snapshot is overwritten), and by the new `redactCheckoutSessions` (`privacy.manage`, audit `privacy.redact_sessions` with a hashed key) for a buyer who never ordered; `/seller/privacy` shows the number of matching sessions and the button.

## Decisions and defaults taken (no owner decision was needed)
1. Single resume semantics: a token names exactly one session; repeated clicks only rebind the same cart (harmless, no data shown); the link is dead once the session is recovered, expired (exactly 7 days), purged, or its cart is empty. The TASKS text has no stronger "single use" wording.
2. Recovered marking matches the order's own cart only (not "same phone"), so the Recovery Rate cannot be inflated by an unrelated order of the same number.
3. A recovered session drops its typed contact immediately (data minimisation: the contact lives on the order).
4. The 60-minute and 30-day figures are task text; they are code constants, not retention-policy rows (the T-74 framework stays off for them). The 60-minute rule is also enforced by the database guard.
5. The resume page does not prefill buyer data from the session (a forwarded link would otherwise hand a stranger the buyer's contact).
6. Provider status codes are recognised by shape (upper-case words) instead of importing the `PROVIDER_STATUS` vocabulary into `privacy.ts`, to avoid an import cycle (`fulfillment` → `orders` → `signals` → `privacy`).

## DEFERRED (exact missing decision or fact)
- **Legal basis of the capture.** The task text requires a notice and the build shows one next to the contact fields; whether UU PDP needs an explicit opt-in (a checkbox that gates capture) instead of a notice, and the 30-day period itself, are privacy-owner decisions (Q-11). Switching to opt-in is a one-line gate in `CaptureProgress`.
- **Who may contact buyers by WhatsApp.** Owner and staff are allowed (they already see the same phones on orders). If the owner wants owner-only, change `carts.recover`/`carts.read` in the capability map.
- **Schedule of `cleanup.ts`.** The 60-minute sweep needs the command at least every 15 minutes; the deployment (cron/Coolify scheduler) is an ops decision outside this worktree (docs/DEPLOY-COOLIFY.md and RUNBOOK have no row for it yet).
- **Prefilled resume.** Prefilling the buyer's typed contact on the resumed checkout would be a UX gain but exposes the contact to whoever holds a forwarded link; not built (decision 5). Needs a product/privacy call.
- **Production key.** `KEYRING_CHECKOUT_RESUME` has only dev/test/e2e placeholders; the owner generates the production ring (secret store).
