## Decisions and defaults

- **Mailer**: `Mailer.send({ to, subject, text })`; the only implementation stores mail in `mail_outbox` (no provider, no network). Mail text is Indonesian. Swap-in point: `dbMailer(db())` in `apps/web/src/lib/auth.ts` and `seller/actions.ts`.
- **Reset token**: Better Auth verification row, 60 min, single use (`consumeVerificationValue`), link = Better Auth callback `/api/auth/reset-password/<token>?callbackURL=/account/recovery/reset`, which redirects with `?token=` or `?error=INVALID_TOKEN`. Requesting a reset answers identically for unknown e-mails (Better Auth 1.7.7 `password.mjs` also simulates the lookup against timing). Reset revokes all sessions (`revokeSessionsOnPasswordReset`, verified in `password.mjs`) and writes audit `password.reset`. Minimum password length is Better Auth's default (8).
- **Invitation**: 32 random bytes base64url; only SHA-256 hex stored; TTL 7 days (`INVITATION_TTL_MS`); single use; one live invitation per e-mail per store (a new invite revokes the pending one); existing members cannot be invited; owners may assign `owner` or `staff`, staff have no `members.manage` capability (and an explicit authority map rejects anything else). Accepting checks the store is active, locks the invitation row, and for a new account creates `user` + credential `account` rows (same shape as the seed and Better Auth's own sign-up) inside the same transaction. A signed-in user must match the invited e-mail (case-insensitive). `previewInvitation` tells the token holder whether an account already exists for the invited address (needed to choose "sign in" vs "create account"); the token itself is only ever in the e-mail.
- **Public sign-up stays disabled** (`disableSignUp: true`); accounts come from the seed or an invitation only.
- **Session lifecycle**: membership is checked per request (`sellerContext`), so role changes/removal apply on the next request (test proves it). Removal also deletes `session` rows when the user has no other membership and no `platform_operator` row. Password reset deletes all sessions. MFA enrolment calls `/revoke-other-sessions` so pre-enrolment sessions do not survive.
- **MFA policy**: TOTP (SHA-1, 6 digits, 30 s, Better Auth default window ±1) via the two-factor plugin; e-mail/SMS OTP is not configured so `method: "otp"` is refused by the plugin. `user.twoFactorEnabled` becomes true only after `/two-factor/verify-totp` succeeds. `/admin` requires it (server-side in `context.ts`); sellers may enrol voluntarily at `/account/security`. Backup codes: plugin default 10, shown once. Trust-device is never requested by our forms. Account lockout after 10 failed sign-in verifications is the plugin default. No QR image: the secret is shown as a manual key plus the `otpauth://` URI (a QR encoder would be a new dependency — deliberate ceiling).
- **Seeded operator enrolment**: `admin@bukalaris.local` is seeded without MFA. First `/admin` visit redirects to `/account/security?next=/admin`; enter the dev password, add the manual key to an authenticator app, enter the 6-digit code, store the backup codes, then "Lanjut ke Super Admin". The e2e suite does exactly this (first project enrols through the UI; the second project signs in with a computed code).
- **Rate limits** (Better Auth production defaults, unchanged): sign-in 3/10 s, `/request-password-reset` 3/60 s, `/two-factor/*` 3/10 s per IP, in-memory. The e2e helpers wait a 429 out instead of disabling the limiter (the recovery test therefore takes ~60 s longer in the second project).
- **Dev outbox**: `/dev/outbox` lists the newest 50 mails (links contain tokens). Hidden in production unless `DEV_OUTBOX=1`; the e2e suite asserts the 404 and reads mail from the database directly.

## Open issues / not done

- No real e-mail provider; `Mailer` is the seam. Delivery, bounces, templates and sender domain are M3+ work.
- Rate-limit storage is in memory per process (Better Auth default); multi-instance needs `secondaryStorage` or `customStorage`.
- No QR code for TOTP enrolment (manual key + otpauth URI only).
- No "regenerate backup codes" / "disable MFA" UI; Better Auth routes exist (`/two-factor/generate-backup-codes`, `/two-factor/disable`) but are not surfaced.
- MFA enrolment itself is not written to `audit_log` (Better Auth handles the state change); password reset and all invitation/membership actions are.
- Invitations are not listed or revocable by platform operators; owner-only.
- The seed does not pre-enrol the operator (by design, so enrolment is testable); document the first-login step in STATUS at merge.
