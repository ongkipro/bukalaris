## Behaviour and safety properties

- **Tenant isolation.** Seller functions take a `SellerScope`, run inside `inStore`, and filter by `scope.storeId`; the order is read from the seller's store only (another store's order → `not_found`). `shipment` has FORCE RLS with the same `tenant_isolation` policy as 0007 (test: app role sees 0 rows without a context, only its own store's row inside it). The buyer link resolves the store from the signed order id (platform pool, ADR-0005 §4), then reads in that store context. Worker handlers run on the platform pool and wrap result writes in `withStore`.
- **Money.** `cod_amount` is integer IDR (`bigint`), copied from the server-side order `total`; prepaid bookings send `goodsValue` = order subtotal.
- **Exactly-once booking.** One shipment row per order (unique), one job per `(shipment, attempt)` outbox key; the order row lock serialises concurrent clicks; a job whose `attempt` is not the shipment's current `booking_attempts` is ignored (stale job after a retry); a job re-run after a lost lease finds the row past `queued` and does nothing; a row left in `booking` by a dead worker fails closed (no blind second `createOrder`). **Only 409 and 429 retry a provider write** (the provider created nothing); timeout, network and 5xx leave the outcome unknown, so the shipment goes to `failed` with "periksa dashboard Mengantar sebelum mencoba lagi". Provider writes are serialised per platform account with `pg_advisory_xact_lock` (409 rule).
- **Insufficient balance.** Provider order without resi → `awaiting_balance` with an explicit message, no tracking poll. Seller "Coba lagi" → `payUnpaid` once (under the lock) → a tracking read fetches the resi (a failed read retries on its own and never repeats the payment) → `booked` + order shipped.
- **Order transitions.** A resi moves `placed → processing → shipped` (resi stored on the order, one "shipped" mail intent); delivery moves `shipped → completed`; actor = the seller who requested the booking. An order shipped by hand keeps its own resi. An order cancelled before the worker ran is not booked.
- **Tracking.** `shipment.track` is read-only, outside any transaction; polls at 15 min doubling to a 6 h ceiling, max 60 per shipment; stops at `delivered/returned/cancelled/failed`; unknown provider statuses keep the state and are shown verbatim.
- **Write lock.** No code path can call Mengantar writes without `MENGANTAR_WRITE_ENABLED=1` (client-level); with credentials but no flag the booking fails with `WRITE_DISABLED_MESSAGE` (test proves `fetch` is never called).
- **COD (Q-17).** Refused in `bookShipment` and re-checked in the worker unless `ALLOW_COD_BOOKING=1`; the UI shows the Q-17 notice instead of the button.

## Fixes made in this session (review of the inherited uncommitted work)

1. Timeouts / network errors / 5xx on `createOrder` were retried by the outbox → possible duplicate provider order. Now fail closed (`isRetryableBookingError` = 409/429 only; `UNCERTAIN_MESSAGE`). Test updated to prove no retry and one provider order.
2. Retrying an `awaiting_balance` shipment set it back to `awaiting_balance`, so every extra click enqueued another `payUnpaid`, and a re-run of the original job could pay without a seller request. Retry now resets to `queued` (duplicate click → same attempt) and the handler acts only for the current attempt.
3. A failed tracking read after a successful `payUnpaid` re-ran the whole job (second payment). The resi is now fetched by a separate `shipment.track` job.
4. Dev database was unseeded, so `ops.spec.ts:124` (standalone server uses `PLATFORM_DATABASE_URL` = dev DB) answered 404; fixed locally with `pnpm db:migrate && pnpm db:seed` (environment only, no code).
