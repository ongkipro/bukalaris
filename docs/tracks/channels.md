## Decisions and defaults

- **Token format**: `blsk_<prefix>_<secret>` — prefix = 6 random bytes
  base64url (8 chars, shown in the list as `blsk_<prefix>_…`), secret = 32
  random bytes base64url (43 chars). Stored: SHA-256 hex of the whole token
  (unique) + prefix. Verification: lookup candidates by prefix, then
  `crypto.timingSafeEqual` on the hashes. The plaintext exists only in the
  server-action result rendered once; it never enters a URL, cookie, log or
  audit row (audit rows record `channel.create:<id>` / `channel.revoke:<id>`).
- **One credential per channel** (lazy ceiling): rotation = create a
  replacement channel → deploy → revoke the old one (the IAM-11 flow). The
  data-model's separate "Channel Credential" record is not needed for that.
- **Lifetimes**: channel expiry optional (`expires_at` null = until revoked);
  an expired channel is denied like a revoked one and listed as "Kedaluwarsa".
  Handoff TTL 10 minutes (`HANDOFF_TTL_MS`). Carts have no expiry (D-6).
- **Handoff**: 32 random bytes base64url (43 chars) in the URL; only its
  SHA-256 is stored, bound to store + cart + channel. Exchange is one atomic
  `UPDATE … SET consumed_at = now() WHERE code_hash = ? AND consumed_at IS NULL
  AND expires_at > now()`; after that the channel must be live, the store
  active and the cart still open, otherwise the (already consumed) code yields
  nothing. Success sets `bl_cart_<storeId>` with the existing `cartCookie()` +
  `cookieOpts` and redirects with a relative `Location` (the standalone
  server reports `0.0.0.0` as its own host, so an absolute URL built from
  `request.url` broke the cookie — found by the e2e run), `Referrer-Policy:
  no-referrer`, `Cache-Control: no-store`.
- **`checkout_url` origin**: `CHECKOUT_ORIGIN` → `BETTER_AUTH_URL` → request
  origin (dev fallback only; deployments must set one of the first two,
  ARCH-7 "separate configuration values").
- **Cart capability**: per D-6 the random cart UUID is the capability; the
  API requires the channel token AND the cart id, and the cart must be an open
  cart of the channel's store (`ownsOpenCart`), otherwise `404 cart_not_found`.
  No separate `cart_capability` header, no revision counter, no
  `Idempotency-Key` on cart mutations (ceilings recorded in the spec notes).
- **Return link allowlist**: built server-side from the stored origin + return
  path of the channel whose consumed handoff produced the cart; shown only
  while that channel is live. Origin validation: absolute URL, `https:` (or
  `http:` for `localhost`/`127.0.0.1`/`*.localhost`), no credentials, path,
  query or hash; return path must match `^/(?!/)\S*$` (no `//host`, no scheme).
- **JSON contract**: numeric ids as strings; money as `{amount: integer IDR,
  currency: "IDR"}`; every response `Cache-Control: no-store`; no CORS headers
  (server-to-server tokens, IAM-11 "CORS is not authorization").
- **Error codes** (`{code, message, correlation_id[, field_errors]}`):
  `401 unauthorized` (missing/malformed/unknown/revoked/expired token),
  `403 store_unavailable` (suspended store), `404 not_found` (product/variant),
  `404 cart_not_found`, `409 empty` (handoff on an empty cart),
  `409 cart_checked_out`, `422 validation` (+`field_errors`),
  `400 invalid_json`; other `DomainError`s map to 409 with their code.
  `correlation_id` echoes `X-Correlation-ID` when present (ops track) else a UUID.
- **Capability**: `integrations.manage` → owner only. Staff see the page with
  an explanation and no list.
- **Native storefront unchanged**: `/s/<slug>` cart actions and `/checkout`
  keep working as in M1 (purchase e2e still passes).

### OpenAPI — implemented vs still proposed

`x-status: proposed` stays on every operation because `check-spec.py` requires
it; implemented operations carry an `x-implemented` note with the real path.
Real paths live under `/api/storefront/v1/**` on the app origin (the spec's
`https://app.bukalaris.com/api/v1` server is still the proposal).

| Operation | Status | Shape change in the spec |
|---|---|---|
| `listStorefrontProducts` | implemented | security: `storefrontToken` only; cursor/limit/q/collection params removed; `PublicProductList.items` → new `PublicProductSummary`, no `next_cursor` |
| `getStorefrontProduct` | implemented | security: token only; aliases not implemented |
| `createCart` | implemented | token only; `Idempotency-Key` removed; `CartCreated` = `{cart}` (no `cart_capability`) |
| `getCart` | implemented | token only; `Cart` without `revision`/`expires_at`; `CartLine` without `id` |
| `addCartItem` | implemented | token only; `CartItemAdd` without `expected_revision`; no `Idempotency-Key` |
| `updateCartItem` | implemented | token only; `item_id` = variant id; `CartItemEdit` = `{quantity 0..99}` |
| `createCheckoutHandoff` | implemented | token only; `CheckoutHandoffInput` = `{}`; no `Idempotency-Key` (each call issues a new code) |
| `listStorefrontChannels`, `createStorefrontChannel`, `revokeStorefrontChannel` | implemented as Seller Admin server actions, no HTTP route | `StorefrontChannelInput`: single `return_path`, optional `expires_at`; `StorefrontChannel`: `+return_path`, nullable `expires_at`, no `revision`; revoke has no `RevisionInput` body |
| `getStorefrontConfig`, collections/pages, `getOrderOutcome`, `/checkout/sessions/*` (`getHostedCheckout`, `quoteCheckout`, `submitCheckout`) | still proposed | untouched; hosted checkout remains the M1 server-action form, the "checkout session" is the existing per-store cart cookie |

## Tests

`packages/db/test/channels.test.ts`:
1. stores only a hash, token shown once verifies; malformed/tampered/wrong-scheme tokens denied
2. revoked and expired tokens denied; suspended store → `store_unavailable`; double revoke → `not_found`
3. staff forbidden (`integrations.manage`); origin/return-path/expiry validation incl. `//evil`, `javascript:`, http non-localhost
4. channel A cannot read store B's products or carts (`ownsOpenCart`, `getCart`, `createHandoff`, `setCartLine`); empty cart cannot be handed off
5. handoff consumed exactly once under two concurrent exchanges; replay null; return target = registered origin + path; hidden after revoke
6. expired handoff, handoff for a checked-out cart, unused handoff of a revoked channel, garbage codes → all null

`apps/web/e2e/channels.spec.ts` (one flow, both viewports): owner creates a
channel and reads the one-time token (not in URL; reload shows only the
prefix) → Playwright `request` acts as the external backend with the bearer
token: 401 without token, list products (draft and other-store products
hidden, ids strings, `no-store`, no CORS header), product detail, create cart,
add item (subtotal 178 000), tampered price → 422, unknown cart → 404, create
handoff → browser opens `checkout_url`, lands on `/checkout?store=toko-a`,
completes checkout to confirmation (`Rp 193.000`), return link ==
`https://toko-ayu.example/thanks` → replaying the URL lands on
`/checkout/h/invalid` and the cart is 404 via the API → revoke in the UI →
token gets `401 unauthorized`.

## Open issues / not done

- No HTTP routes for channel management (UI server actions only); no
  idempotent replay on `createCart`/`addCartItem`/`createCheckoutHandoff`;
  no cart revision or expiry; no pagination on product list.
- No rate limiting or abuse controls on the Storefront API (SEC-13 /
  16-OBSERVABILITY proposals); handoff codes are 256-bit so brute force is not
  practical, but a limiter still belongs at the edge.
- `CHECKOUT_ORIGIN` is read but not documented in `.env.example` (root file,
  not owned by this track) — orchestrator to add alongside `BETTER_AUTH_URL`.
- Revocation does not invalidate a hosted checkout already opened via an
  exchanged handoff (the buyer keeps the cart cookie); IAM-11 leaves that
  policy to be chosen before release. Unused handoffs are denied.
- Token prefix lookup assumes few collisions (8 random base64url chars); the
  constant-time compare loops over all candidates.
- Shared-file edits to merge: `scoped.ts` (one capability line) and
  `checkout/confirmation/page.tsx` (return link).
