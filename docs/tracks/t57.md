# T-57 — Global buyer identity core and automatic checkout association (track `t57`, patch `T57Buyer`)

Local, uncommitted work in an isolated copy on top of the wave 1 and 2 overlay (Goal Mode, D-20 to D-22). Nothing deployed, no provider called, no OTP, no portal. Contacts in every test are synthetic. Association is **not** verification, login, prefill or merge: no row written by this task carries a verification time, a binding, a session or a returned profile.

## What changed

New context `packages/db/src/buyer/`:

|---|---|

## Decisions and defaults taken

1. **Two keys, one module.** `phoneLookupKey` keeps landlines and foreign numbers findable for risk lookups and data-subject requests (a seller must still find them); only `normalizePhone` decides identity (`628…` + 7..12 digits, UNVERIFIED structural bracket inside E.164, no numbering-plan claim). No country is guessed: bare digits without `+`, `00`, `0` or `62` have no identity.
2. **SQL port instead of caller-supplied canonical values.** The resolver is target-bound: the caller names `(store, order)` only and the function derives the keys from the committed snapshot, so a compromised platform login cannot attach a value of its choosing. That needs the normalization in SQL; `t57-normalize.test.ts` runs one table through both implementations and fails on any difference.
3. **Class `buyer` for all five tables, platform column empty.** `buyer_identity_event` is class `buyer` too (policy present, no app grant, so no login role reads the evidence; restricted service reads are T-72). The default privileges of the expand step would give the platform login DML on the new tables; the migration revokes it explicitly, so `bukalaris_platform` reaches identity only through `buyer_resolve_order`. The app role keeps `SELECT` under own-buyer RLS (the T-58 portal reads); it gets **no** write grant (also not on `buyer_address`: the portal adds it with its service). Accepted limit, unchanged from ADR-0005 amendment: any SQL running as `bukalaris_app` can set `app.buyer_id` and read a chosen buyer's rows; the defence is the absence of a raw-SQL surface, and no cross-store or cross-buyer read exists outside the definer function.
3a. **Event table is not restricted-owned.** ADR-0005 says restricted for the platform role; the property (no platform privilege, definer-only writes, append-only trigger that also stops the owner and superuser) holds without moving ownership to `bukalaris_restricted`, which would need a NOBYPASSRLS definer owner that cannot read `order`.
4. **OPEN recommended variant taken as default.** ADR-0010 step 6 (recommended, not decided): an observed (not `bound`) e-mail of an e-mail-only buyer is **not** given a submitted phone; a new buyer is created, the e-mail stays, no `email_phone_mismatch` (that event is for a different live phone). `EMAIL_MATCH_REQUIRES_BOUND` in `buyer/resolve.ts` is passed to the function; `false` reproduces the literal ADR algorithm and a test pins that path.
5. **`buyer.resolve` is bulk priority.** It runs behind payments and the order e-mails (identity-class priority made a mixed batch push the notification of the last order out of the default batch of ten in `notify.test.ts`; more importantly a checkout flood must not delay a payment instruction). Replay-safe, so an audited requeue is allowed.
6. **Revoked identifiers.** Nothing revokes an identifier yet. A revoked key is never chosen and never re-attached; if no identifier of an order can be attached the function raises (visible dead job) instead of inventing a policy: recycling is OPEN.
7. **Order without a usable contact** (redacted, landline or foreign number and no e-mail) creates no buyer: outcome `no_identifier`, job done. A buyer with no identifier would be an uncorrelatable orphan.
8. **No raw contact in evidence.** Events carry ids, event type, actor (`system`/`buyer.resolve`) and the job id as request id; a test asserts no digit run or `@` appears.
9. **Key ring is a hard dependency of checkout.** SEC-22: no fallback, no unkeyed hash. Missing or malformed `KEYRING_BUYER_FINGERPRINT` makes `placeOrder` throw `buyer_key_unavailable` before anything is written (test). Local `.env` files need the new line (`.env.example`); vitest and Playwright set a placeholder themselves.
10. **No guard on DELETE of buyer, identifier or link** beyond privileges (nobody holds them): global deletion/closure is OPEN and must replace them deliberately; the link guard also forbids moving a link (a merge is not implemented and would replace the guard).

## DEFERRED (with the exact missing decision)

- **OTP / magic-link proof, verified and bound identifiers, confirmed links, portal sessions** (T-58): channel/provider/cost, delivery limits and lifetimes (product and security owners). The columns and CHECKs exist; nothing writes `verified_at`, `binding_state='bound'` or `access_state='confirmed'`.
- **Recycled and shared numbers, revocation, reuse of a revoked identifier**: security and privacy owners. The unique key keeps revoked values; the resolver raises when only revoked identifiers remain.
- **Merge UX and any staff merge, contested observed-identifier claims**: product/security owners (D6: staff merge stays disabled). The link guard forbids reassignment; the events `merge_*` exist as names only.
- **Global deletion/closure, retention periods of the five tables, restore reapplication**: privacy/legal owners. No `retention_class` row, no purge, no delete guard beyond privileges.
- **Minors**: legal/privacy owners.
- **Backfill of existing orders**: data owner (collision review); not built, no retrospective merge.
- **Authenticated prefill**: product/privacy/security owners; nothing in the checkout response or any endpoint reads the buyer tables.
- **Checkout notice text** (global association, controller, purpose, rights, UU PDP consent): privacy owner and qualified legal review; no notice is rendered.
- **Completion/recovery target of the asynchronous synchronization** (ADR-0010 section 4): product/operations. The backlog is observable (`jobLagByKind('buyer.resolve')`, `deadLetters`) but no alert threshold or SLA number exists (D-22 item 3: it would be a named setting).
- **The OPEN e-mail-bound rule** is implemented as the recommended default and can be reversed with one constant; the owner has not decided it.
- **Buyer-side services**: `BuyerScope`, own-history projection, address write grant and service, identity-event read service (T-58, T-72); `buyer_address` has the table, constraint and RLS, no writer.
- **Affiliate self-referral wiring** (T-52): `samePhoneIdentity` is the contract; no affiliate code exists yet.
- **Rate-limit rows for OTP request/verify** (RL-OTP-*): T-58 (no buyer-facing request exists in T-57; checkout keeps its existing per-IP, per-cart, per-phone limits).

## Export, redaction, rate-limit and audit rules for the identity tables (slice 4)

- **Inventory:** five new rows in `BUYER_DATA_INVENTORY` (handling `global`, plus `not_personal` for the primary-phone reference) and matching rows in `docs/13-COMPLIANCE-PRIVACY.md`. A seller's export and redaction stay per store and never read these tables; a redacted snapshot is never resurrected from them (tests). Portal export, closure and retention are T-58 and OPEN.
- **Rate limits:** the resolver is worker-only (no request path to throttle). Checkout keeps its three limits; the per-phone key is a keyed fingerprint. OTP/recovery limits are T-58.
- **Audit:** every association writes append-only events (no raw contact); conflict and mismatch events name the other buyer internally only; nothing in a checkout response, seller view or affiliate result exposes them. Reads of the events are not granted to any login role.
- **Observing the backlog:** `jobLagByKind(db, now)` per kind (pending, running, dead, unknown, oldest due age) and `deadLetters()`; `buyer.resolve` is replay-safe, so an operator may requeue a dead job (`ops.jobs.manage`).
