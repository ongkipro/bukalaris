## Decisions and defaults taken (all revisable)

1. Rejection of a payout still `requested` stays single-operator (nothing was approved or sent; the seller's money simply returns). Rejection of a payout in `processing`, and EVERY refund failure, is four-eyes (`payout.reject_processing`, `refund.fail`, 24 h validity like the other transfer rules).
2. An unknown outcome is never claimed again; the operator who reported it may record the transfer evidence after the lease (paid), or a second person approves the no-transfer statement (rejected). A failed refund stays visible as `refunds_failed` until a new refund is opened for the order (`reopenFailedRefund`, `refunds.process`).
3. The destination hold is the DB setting `payout_control.destination_hold_hours` (default 72, CHECK 1..720; D-19 "Owner-configurable"); there is no console setter yet (see DEFERRED).
4. The post-restore freeze flips with `payouts.process` + a reason (not four-eyes): freezing must be fast. Unfreezing has no expiry. `ledger.release` is NOT frozen (it only moves facts already true: delivered and reconciled).
5. SA-08 holds both queues (UX-14: payout and non-COD refund queue); SA-26 holds the money position, unknown transfers and late-payment obligations; the brief's "SA-26 (refund queue)" is therefore served by SA-08's refund tab plus SA-26's late-payment list.
6. Seller step-up uses the 6-digit code typed in the form (verified by this surface's Better Auth for THIS session, then the single-use database proof); the code is never stored.
