## Design decisions

1. **Platform-wide jobs: `job.store_id` becomes nullable, guarded by a registry.** `platform_job_kind(kind PK)` is written by migrations only (platform role: SELECT). Trigger `job_platform_kind_guard` (BEFORE INSERT/UPDATE OF store_id, kind; SECURITY DEFINER, fixed search_path) raises `check_violation` when `store_id IS NULL` and the kind is not registered, even for the BYPASSRLS platform role. A CHECK cannot read a table and a hard-coded kind list would need a migration per kind with no registry; the registry means a new periodic kind is one `INSERT` in its own migration. Tenant isolation is unchanged: the policy `store_id = app_store_id()` never matches NULL, so the app role cannot read or insert store-less rows (tests: `scheduler.test.ts` "only registered platform kinds may omit the store"). `enqueue` still requires a store; `enqueuePlatform` is the only NULL path. Handlers are typed `JobHandler` (store: number) or `PlatformJobHandler` (store: null) and `runOnce` refuses a scope mismatch, so the ~8 existing `j.storeId` call sites compile unchanged.
2. **Cursor table `scheduler_cursor(kind, last_period_start)`** (not in DATA-16). Without it the current period of a monthly kind would be re-inserted each tick once retention purged its `done` row (the unique key lives in the purged row). The cursor, not the job table, remembers what was enqueued, so retention can never re-create a period (test "purging a finished periodic job never re-creates its period"). Catch-up = periods after the cursor, at most `schedule.catchUp` older ones plus the current one; older ones are skipped by design. `scheduler_heartbeat` gets `tick_interval_ms` (stale = older than 2 x interval, OBS-6; `missedTicks` overridable).
3. **Tick = one transaction** that locks the heartbeat row, enqueues, moves cursors and writes the heartbeat. Concurrent ticks serialise on the lock and the unique key makes inserts no-ops; a failure (for example an unregistered kind) rolls everything back so the heartbeat goes stale and the failure is visible. The worker passes `tickMs + pollMs` as the interval (its real worst-case gap). `/api/ready` was not extended (the web pool has no grant on the heartbeat); `schedulerHealth(db, {now})` is the query for the health view and alerts.
4. **`failed` renamed `dead`** (JOB-22, OBS-7); status set is `pending|running|done|dead|unknown`. Backfill statement in the pending SQL (see folding order).
5. **Priority and lease are fixed on the row at enqueue** from the kind's policy (`kindPolicy`: built-in table in `jobs.ts` plus the optional third argument of `registerHandler`). Classes: money 0 (`payment.instruction`, `shipment.book`, `shipment.track`), identity 1 (`order.notify`), bulk 2 (everything else, default). Claim order is `priority, next_attempt_at, id`, index `job_claim_idx` rebuilt on those columns. Ceiling: strict priority, no aging, no per-kind concurrency caps or reserved capacity (OBS-7 mentions them); a permanent money flood would starve bulk. A change of policy applies to newly enqueued rows only.
6. **Lease/heartbeat.** `runOnce` extends the leases of every unfinished job of its batch at one third of the shortest lease, so a long handler and the jobs queued behind it in the same batch keep their claims. `heartbeatJobs` is also exported for handlers.
7. **`unknown` and the fence (D-21).** `markDispatched(db, j)` commits `dispatched_at` while the lease is live (throws `LeaseLostError` otherwise, so nothing is sent without a lease). A job with `dispatched_at` set that crashes (lease expiry) or whose handler throws becomes `unknown`, is never claimed again, and the DB constraint `job_dispatch_chk` forbids `pending` with `dispatched_at`. A crash before the fence is requeued as before. Leaving `unknown` needs `resolveUnknownJob` (confirmed -> `done`; absent -> `pending`, the only re-dispatch path) or a registered reconciler. A job that crashes the worker on every attempt becomes `dead` at the attempt ceiling instead of being reclaimed forever. Existing handlers do not use the fence yet (their own idempotency is unchanged); T-37/T-49/T-48 adopt it for provider calls.
8. **Audited requeue/reconcile/rebuild** use `audit_log` (`jobs.requeue`, `jobs.reconcile`, `projection.rebuild`, `retention.set`), in the same transaction. They take the Owner console `OperatorScope` and require `ops.jobs.manage` themselves (wave 1 review; `requirePlatformCap`); only the automatic reconciler settles jobs without the capability, as the system actor. Requeue is refused unless the job is `dead` and its kind is replay-safe (`payment.instruction`, `shipment.track`, `order.notify`, `signal.deliver`, retention kinds; `shipment.book` is not: owning service reconciles). Reconcilers record the actor `system:job-reconciler`. Cancel of a dead job (OBS-7 mentions "requeueing or cancelling") is not implemented.
9. **Rebuild hook.** `registerProjection(name, rebuild)`, `rebuildProjection(op, {name, reason})`: one transaction, advisory lock per name (concurrent rebuilds serialise, each is a full rebuild), audited, rolled back on failure. T-52 registers `affiliate_catalog`; tested with a fixture table pair.
10. **Retention.** Registry `retention_class(class, table_name, time_column, row_filter)` seeded by the SQL; period table `retention_policy(class, period_days >= 1)` has no seed and no default: no row = `retention_purge*` returns 0. The period is not an argument and neither is the clock (the database clock is used; a caller cannot pass "now = far future"). `retention_purge(class, batch)` is SECURITY DEFINER owned by `bukalaris_owner`, `search_path = pg_catalog, pg_temp`, every reference schema-qualified, raises `insufficient_privilege` when the caller's temp schema holds a relation named `pg_*`, and adds `AND NOT EXISTS` for every foreign key found in `pg_constraint` that references the table (single, composite and `ON DELETE CASCADE`). EXECUTE: none on the generic function; the five named wrappers (`retention_purge_signal_event|system_log|audit_log|job|job_dead`) go to `bukalaris_platform` only. Classes: `signal_event` skips `pending` rows; `job` = `done` only; `job_dead` = `dead` only (separate so dead letters, which OBS-7 keeps, go only when the owner sets that period); `pending`, `running`, `unknown` are never purged. Sweeps are daily platform jobs created by the enqueuer; the handler runs up to 50 batches of 1000.
11. Registry/state tables carry no RLS and no app grant (platform class, the `platform_operator` convention that `rls.test.ts` asserts); the platform role gets only what it needs (registries SELECT; heartbeat/cursor no DELETE).

## DEFERRED

- **Monthly partitioning of the log tables.** Not additive: Postgres cannot convert a populated table in place; it needs a new partitioned table, a data-moving copy and a swap (owner approval at deploy time), and the primary key must then include the partition column. For `job` this also breaks the exactly-once design, because `UNIQUE(kind, key)` cannot be enforced across partitions unless the key carries `created_at`. The purge function deletes row by row in bounded batches instead, which is correct for the volumes in DATA-16 until the measured thresholds are reached (5 million rows for `job`).
- **Access-event class (`personal_data_access_event`, JOB-31):** the table does not exist yet (T-62). Its `retention_class` row, wrapper function and sweep kind ship with the migration that creates it; `retention.ts` has one `SWEEPS` entry to add.
- **Restore rehearsal: decryption of escrowed credentials** needs the key ring and sealed columns of T-48/T-65. `LIVE_SYSTEM_IDENTIFIER` must be set to production's `select system_identifier from pg_control_system()` (not available here); unset means the guard is inactive and the summary says so.
- **`ops.jobs.manage` enforcement**: DONE after the wave 1 review (all four services check it; refusal tests in `review-findings.test.ts`). Retention periods are set only through the owner-side `retention_set_period()`; the `audit_log` class has NO setter until operator identity is restricted (T-59b), because the platform login can read the holders of `ops.jobs.manage` and could name one as the actor.
- Owner console screens (dead-letter list, retention settings, scheduler status) and alert delivery (OBS-6 sink is OPEN); the functions exist.
- Contract step: platform still holds DELETE on `audit_log`, `system_log`, `signal_event`, `job` (0007 default grants). Revoking it so that only the purge functions can delete is the T-59 contract step (D-22 item 4); until then "narrow grants" is true for the new functions, not yet for the tables.
