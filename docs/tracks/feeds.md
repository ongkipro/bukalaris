## Feed contract (as implemented)

Grain (Q-7, D-8): one item per **variant** of an **active** product; `id` = variant catalog id, `item_group_id` = product catalog id, both the same strings the conversion signals send as `content_ids` / group ids (PR-20). A group id is never published as an item id (shared sequence, D-8).

| Field | Meta CSV column | Google RSS element | Value |
|---|---|---|---|
| id | `id` | `g:id` | variant `catalog_id` (string, ≥ 5 digits) |
| group | `item_group_id` | `g:item_group_id` | product `catalog_id` (string) |
| title | `title` | `g:title` | `<product title> - <variant title>`, whitespace collapsed, clipped to 150 (Google's limit; Meta allows 200) |
| description | `description` | `g:description` | product description as plain text (whitespace collapsed; the catalog caps it at 5 000 = Google's limit, Meta allows 9 999); falls back to the title when empty (both platforms require it) |
| availability | `in stock` / `out of stock` | `in_stock` / `out_of_stock` | variant `stock > 0` |
| condition | `new` | `new` | constant |
| price | `<integer> IDR` | `<integer> IDR` | variant price, integer rupiah, ISO 4217 code after a space |
| link | `link` | `g:link` | `<store base>/products/<slug ?? catalog id>` (canonical URL, D-8) |
| image | `image_link` | `g:image_link` | `<store base>/media/<cover id>` (position-0 image) |
| brand | `brand` | `g:brand` | store name (clipped to 70, Google's limit) |

Store base URL (`storeBaseUrl`): `https://<slug>.<STORE_ROOT_DOMAIN>` when `STORE_ROOT_DOMAIN` is set to a real domain (production host mode, HTTPS); otherwise `<BETTER_AUTH_URL>/s/<slug>` (dev/e2e path mode, which a feed validator outside the browser can also resolve). Feed URLs themselves live on the app origin (`<BETTER_AUTH_URL>/feeds/<token>/…`): the token names the store, no host is involved.

Format choice: **Meta = CSV** (first format Meta lists; RFC 4180 — every cell quoted, quotes doubled, CRLF; header row exactly the spec's field names), **Google = RSS 2.0 XML** with `xmlns:g="http://base.google.com/ns/1.0"` and the `g:` prefix on every Merchant attribute; channel `title`/`link`/`description` present (Google requires them). XML text escapes `& < > " '` and drops XML-1.0-illegal control characters; UTF-8 throughout (unicode passes untouched).

Missing image: both platforms reject an item without `image_link`, so a product with no image is **left out** of both feeds rather than emitted invalid; the settings section shows "Aktif tanpa gambar (dilewati)" with the count and tells the seller where to fix it. Decision recorded here, not in D-x (reversible UI/feed default).

Token: `blfd_<8>_<43>` (6 + 32 random bytes base64url), SHA-256 hash stored, prefix indexed for lookup, `timingSafeEqual` on the hash; the plaintext appears once in the action result. Regenerate revokes the current token in the same transaction; at most one active token per store (partial unique index). Verification pattern is the same as channel tokens (ADR-0005 §4): prefix → `(store_id, hash, status)` through the platform pool, then store slug read in the store's RLS context, then `storefrontScope` (active store only). Audit rows `feed_token.create:<id>` / `feed_token.revoke:<id>`.

## Issues found and fixed on resume

1. **No abuse limit on a valid token** (review item "cache/abuse limits"): every fetch re-renders the whole catalog, so a leaked URL could be hammered. Added a per-store budget on the existing T-30 counter (`limitFeedFetch`, 60 / hour, 429 + `Retry-After`); unknown tokens still cost only the regex + one indexed prefix lookup and are not counted. New Vitest case proves the 61st fetch waits and another store is unaffected.
2. **E2E race in `feeds.spec.ts`** (the real cause of the recurring `content.spec:44` desktop failure, not contention): the spec clicked the product link and immediately called the non-waiting `count()` on the image list; it read 0 before the page loaded and uploaded a third image, so `content.spec`'s "one move up is enough for two images" no longer made its image the cover. Fixed by waiting for the product page (`Berkas gambar` visible) before counting.
3. Cross-track nav overflow (`ui.spec` shell, desktop): identical one-class change from the `dashboard` track (see shared edits).
4. `ops.spec:124` 404: environment only — the dev DB `bukalaris_feeds` lacked migrations/seed; fixed with `pnpm db:migrate && pnpm db:seed`, no code.

Flakiness verdict: the Vitest suite passed 3/3 runs (146, 147, 147) with three tracks running; the earlier varying Vitest failures were contention. ## Open issues / ceilings

- `identifier_exists` is not emitted for Google: these are mostly unbranded/custom products without GTIN/MPN and the brand is the store name; Merchant Center may warn per item. Owner decision: emit `identifier_exists = no` (then Google ignores brand) or collect GTIN/MPN per variant later.
- No `google_product_category` / `fb_product_category`, `color`/`size`/`material` variant attributes, `sale_price`, or `additional_image_link`: the catalog has no such fields yet. Google requires a distinguishing attribute (color/size/material/pattern) for grouped variants in some categories — expected first disapproval to watch on the first real submission.
- Feed is rendered on every fetch (no cache/ETag); fine for the catalog sizes of M2. lazy: add `ETag`/`Last-Modified` from `max(updated_at)` when a store passes a few thousand variants.
- Rate limit is per store for valid tokens only (60 / hour); unknown tokens are not throttled (256-bit secret, one indexed lookup). Add an IP dimension if unknown-token floods appear. Counters are cleaned by the existing `cleanup` (older than a day).
- The committed evidence screenshot shows a one-time feed URL from the throwaway e2e database (localhost, revoked later in the same test, DB wiped each run) — not a real credential.
- The Playwright worker logs `poll_failed` for a few seconds at start-up (pre-existing race with the e2e database wipe; it recovers).
